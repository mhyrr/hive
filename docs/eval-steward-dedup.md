The session-scoped in-memory seen-set in `src/lib/steward/context.ts` is directionally correct for suppressing repeated recent results within a single steward session: first load includes current unseen run IDs, subsequent loads omit repeats. The nullable `recentResultsDigest` flow is clean through `src/lib/steward/sections.ts`: `renderCompactState` only renders the section when `recentResultsDigest != null`, so `null` cleanly means “no new results this turn.” The biggest edge case is that dedup side effects happen inside `loadStewardContext`, so any caller that loads context without actually sending a steward turn (for example launch prompt assembly or session prewarm paths) can mark results as seen and suppress them later. A second edge case is timing: run IDs are marked seen before successful turn delivery, so an aborted/failed turn can still consume results. A third edge case is sampling: runtime state only carries the most recent N results (currently 10), so if more than N runs finish between turns, older unseen results can be skipped entirely. Also, `src/lib/state.ts` now has persistent seen-results helpers (`readSeenResultRunIds`/`markSeenResultRunIds`) that are not wired into this path, which creates a split-brain dedup story (session memory vs. disk state) and raises maintenance risk. Net: the nullable digest plumbing is solid, but the seen-set update point should move to post-delivery (or at least be limited to true steward-turn contexts), and the windowing behavior should be explicitly accepted or widened.
